# Travel Agent V2 产品定义与用户体验

> 状态：V2 当前产品定义，随用户决策持续修订。本文已吸收入境中国市场验证、Brainstorm V2、既有 V1 产品约束与当前代码实况；研究数字和来源继续只在[市场验证基准](../research/archive/2026-08-20-inbound-china-market-validation.md)维护，产品推演见[Brainstorm V2](../research/archive/2026-08-20-next-iteration-product-brainstorm-v2.md)。

## 产品结论

2026-09-22 已确认、待实现：用户补充要求、来源变化或模型失败后，仍应从同一规划目标和已保存进展接续。原已采用计划与工作草案持续可见，核验状态独立变化；必要问题回答后自动处理对应事项。用户只看到实际变化、明确缺口和必要下一步。实现及共同验收依据为 [14 业务模型](./14-continuous-planning-business-model.md)、[15 上下文与交接](./15-model-context-and-handoff.md)及[主线程开发交接](../research/2026-09-22-continuous-planning-redesign-handoff.md)，不以文档更新表示已上线。

### 自动处理与必要交互（2026-09-21）

当前路径是：表达要求 → 补查与比较 → 更新可撤销草案 → 路线、预算与约束核验 → 必要时只问一个关键问题 → 回答后继续原任务 → 用户采用。只要求局部比较时不强行完整排程；要求完整行程时不能以候选排序结束。明确按钮、计算、有效缓存与已明确的确认直接使用现有工具。

公开可取得的资料由系统补查；用户专属事实、重要约束取舍和新授权才需要提问，并解释回答的影响。模型置信度不能替代事实、锁定、权限或全局可行性。可恢复的额度等待显示“当前方案已保留，稍后自动继续”，用户可以随时停止。

新模板必须经过中文/目标语言校准才可自动调整草案。当前真实 Jev 小样本仍存在误判，因此默认关闭；受控闭环通过不等于商用品质通过。验收依据见[实现记录](../research/2026-09-21-jev-automatic-planning-implementation.md)。

用户验收修复补充（2026-09-21）：

- 完整规划先补目的地、日期、明确人数等必要个人事实，一次只问一项；已提供的其他要求立即保存，未知人数不默认成一人。
- 局部请求按用户指定领域研究。日期等回答使旧草案失效后，自动接续原目标、补查并重排；不能以“已记住”结束。
- 完整草案检查覆盖其实际行程时段的午晚餐；地点与到访分开，一家餐厅可用于多餐，也可同时采用多家餐厅和多个景点。用户自行安排的返程不自动扩展成额外游玩任务。
- 预算和硬性无障碍要求由服务端统一核验，未知的连续无台阶路线不能采用。预算纳入已排餐次、体验次数和市内交通估算；不把“候选可比较”当成“全程可执行”。
- 条件性草案必须展示剩余未知项，不能称为完整核验。已采用与未采用状态以当前数据库为准。仅调整预算保留站序与路线，不重复索要确认。

业务返工补充：拦住错误采用只是底线。超预算时先在原要求内比较替代候选；资料未知时自动定向补查。完成或失败的核验结果都必须回到 Parent，由它解释取舍与下一步，不能在工具成功时强制结束，再用固定文案冒充交付。完整规划按本次委托范围验收：出差不强塞景点，用户自理的返程不强排，住宿晚数与游玩天数分开保存。未通过的草案仍应可查看、刷新恢复，但不能采用。

最新根因、返工与真实业务证据见[业务闭环返工报告](../research/2026-09-21-traveler-business-rework.md)。前一轮[修复与复测](../research/2026-09-21-traveler-acceptance-fixes.md)保留为历史证据，其“已修复”不能解释为完整业务闭环或商用通过。

Travel Agent V2 是**面向入境中国自由行者的旅行执行助手**：出发前把这趟中国旅行准备好，规划时给出一条适合同行人的可执行主路线，旅途中告诉用户现在做什么，发生变化后继续接管。

产品的核心是一个更智能、更 agentic 的旅行规划智能体：它主动理解需求、迭代查证、算账比较、发现并补齐缺口、解释取舍，把吃住行玩组织成可执行方案；对话、地图工作台、预算看板和 Today 都是服务于这个智能体的呈现面，而不是反过来。用户接受以合理等待时间换取规划深度，等待过程必须透明、可打断、部分结果先行。Agentic 规划能力的迭代路径见[智能规划能力产品迭代文档](./11-intelligent-planning-iteration.md)。

首要客群是第一次或第二次来中国、停留四天以上、自己决定大部分吃住行玩、但愿意在官方或授权平台完成预订的自由行与半自由行游客。英文先形成完整闭环；国内 AI 重度用户继续使用同一套规划、地图、长尾发现和局部重排能力，但作为第二增长曲线，不在首屏承受入境准备教育。具体城市只用于覆盖不同旅行结构的测试，不构成单城市产品范围。

产品不再把“生成一份攻略”当作完成。用户真正雇佣它完成的是：

1. 判断这趟旅行是否准备好，哪些事情会在中国现场卡住；
2. 把吃、住、行、玩组成一条能走通的主方案，而不是四份候选清单；
3. 解释为什么某个选择适合这次旅行和这些同行人；
4. 在可信平台完成预订、导航、预约或现场沟通；
5. 在延误、下雨、闭店、走错或体力变化后，只修复受影响部分；
6. 把真实到访结果变成帮助下一位旅行者的决策证据。

## 用苏格拉底式问题检验范围

### 用户缺的是更多旅行信息吗？

不是。搜索、社交、OTA、地图和官方指南已经提供大量信息。缺口是把这些信息翻译成“我现在能不能完成、下一步做什么、失败后怎么办”的连续过程。因此，内容数量不是北极星指标，可执行行动才是。

### 第一屏必须把吃、住、行、玩全部研究完吗？

不必，也不应该让用户等待一份假完整结果。第一屏必须回显旅行理解、与本次旅行有关的准备缺口、已有路线骨架、最多三个关键取舍和一个下一步；完整旅行通常联动吃、住、行、玩，最终可接受方案必须覆盖用户本次委托的领域、日期和必要安排，并通过时间、位置、预算和同行人约束核验。用户明确排除或自行安排的部分不强行补入。

### “小众、当地人知道”是不是产品核心？

它是吸引用户的差异体验，不是独立闭环。一个地点只有在地方特征、来源独立性、旅行适配、路线代价和执行方式都说得清楚时，才进入推荐；否则只是另一条收藏。

### 为什么还要保留登录、全平台、MCP 和中国内容渠道？

它们分别解决连续使用、行前与行中不同设备、外部 Agent 嵌入和长尾线索发现，但都不是首次价值本身。登录延后到保存、跨端、分享或执行动作；各端共享同一旅行状态但不复制同一版面；MCP 复用业务能力而不另做产品；社交渠道先支持用户提供链接，再在授权和隔离成立后自动检索。

### 是否需要重做现有旅行内核？

不需要。共享 TripState、逐人约束、Evidence、Patch 确认、Provider、地图、履约跳转、变化恢复和到访反馈都是可复用基础。V2 主要修正入口、结果层级和行中任务模型，只新增匿名旅行、准备状态、当前执行任务和渠道归因等必要状态，不建立第二套旅行内核。

## V1、研究基准与 V2 的决策追溯

| --- | --- | --- |
| 吃、住、行、玩完整，且共享同一旅行状态 | 保留 | 四条任务链的相互影响仍是 Agent 价值基础 |
| Agent 负责理解、追问、取舍和局部重排；Skill/Provider/MCP 各守边界 | 保留 | 当前内核和安全边界正确，不因目标客群变化而重建 |

  A[免登录输入文字 语音 链接或图片] --> B[回显旅行理解]

  E --> F[在可信平台预订 导航或预约]

黄金路径的第一个价值时刻发生在登录之前：用户在一次输入后，能看懂“系统理解了什么、这趟旅行目前哪里会卡住、建议怎样走、接下来只需做什么”。如果 Provider 暂时缺失，界面保留已确认部分并说明影响和恢复动作，不能用模型记忆补出地点、价格、房态、路线或设施。

## 用户旅程与界面合同

### 1. 免登录开始

- 首页只有一个主输入，支持文字、语音、分享链接和图片；日期、同行人、预算、节奏只作为四个短选择器辅助输入，不形成问卷。
- 用户没有完整日期、出发地或预算时，Agent 先完成不受该字段影响的理解与准备判断，只追问当前最会改变结果的一个问题。
- 匿名旅行只保存非敏感的旅行理解和临时方案。护照、银行卡、支付凭据、手机号、Cookie、Token 和证件影像不进入 Prompt 或旅行状态。
- 保存、跨端继续、分享给同行人或记录执行结果时再要求登录；登录后应合并匿名旅行，不能让用户重新描述。

### 2. 第一份结果

第一份结果不是四栏候选，也不是长篇聊天，而是：

1. 一句话说明整体策略；
2. “我理解的旅行”与可直接纠错的关键信息；
3. 与这趟旅行相关的已准备、待准备和临近出发再核验项；
4. 住宿锚点、主要地点、跨城到达和市内接驳可见的地图路线骨架；
5. 最多三个会明显改变路线的取舍；
6. 一个明确下一步，如补日期、比较住宿、查看跨城交通或保存旅行。

吃、住、行、玩仍是同一旅行状态上的四条任务链。缺少出发地只影响跨城交通，不阻塞目的地内研究；日期不在天气预报窗口时显示何时复核，而不是用当前天气替代未来天气。

### 3. 规划与比较

- 桌面端采用可伸缩的“对话控制区 + 旅行规划工作区”。对话可折叠；工作区先显示抵达、住宿、餐饮、游玩的当前选择，点击一个环节后才展开该领域的横向替代项。地图、时间轴和影响保持在同一工作区，地点完整详情按需打开；不能重新形成三个同宽竖栏，也不能把替代数量和入口藏到用户不知道的抽屉里。
- 地图与路线共享焦点：点击地点卡、路线节点或地图标记会同步当前选择。没有方案时，主工作区显示旅行理解、准备检查和下一步，不留大面积空白。
- 每次只展示两到三个真正改变体验的选择。选择器点击后必须立即更新结果或打开短输入，不能是无反馈标签。
- 地点详情先给一句话低剧透判断，再按需展开实景图、地图、为什么适合、路线代价、营业/预约/排队、语言/支付/过敏、设施、来源、新鲜度和不确定项。
- 只有地点顺序、时间窗、城市移动和同行人约束同时成立时，产品才称为“按天行程”；否则明确显示为路线骨架、候选或待排程。
- 点击候选先进入不落盘试排；地图必须显示跨城到达、住宿、餐饮、体验和每日返回住宿的多点路线，并同步更新时间、交通估价、候选参考价、预算、单段步行/换乘阈值和天气影响。确认前 TripState 不变；替换只修改对应领域并保留其他已确认项。

#### Agent-assisted Trip Workspace

当前地图工作台方向正式锁定为：

1. 地图是 Trip 视图的稳定空间底座，不再作为地点卡旁边的附属预览；桌面端路线/日程与地图约占 56% / 44%，窄屏改为切换而不是压缩。
2. 永久 Session 栏收进 `Trips` drawer；会话管理仍可随时打开，但不长期占用地图和行程宽度。
3. Agent 对话保持约 340px 且可折叠；默认只显示当前决策附近的结论、关键取舍和下一步，完整解释与来源按需展开。
4. Readiness 与 Next Step 合并为工作区顶部一条“出发前还差 N 项”；展开后才显示详细准备卡。
5. 待确认 Proposal 先在整趟安排中显示“当前项、状态和替代数量”，用户选择一个环节后才展开候选轨道，明确区别“试排、已确认、可替换”；详细证据按需打开。决定完成后保留紧凑替换入口，不永久形成第三栏。
6. 用户拖动或换序时只生成 Change Preview，先显示预算、移动、同行人、锁定项和未知项影响，再生成 `TripPatchProposal`；前端不得直接改写 TripState。
7. 产品必须区分四个状态：`候选 → 路线骨架 → Day Timeline → 已确认/已预订`。没有活动时长、时间窗或移动可行性时只能显示路线骨架。
8. 预订、票据、准备、预算、打包和分享在旅行形成后按需进入 `Trip Kit`，不扩张为首屏七个管理页签。
9. 多人协作先服务 OpenDecision：分享关键决定、轻量投票、逐人偏好确认和共享 Today；不新建与 Agent 对话重叠的群聊中心。

### 4. 可信执行

Travel Agent 负责理解、比较、核验、衔接和解释，不重建成熟平台已经做好的交易与导航：

| 执行动作 | 用户必须看到 | 完成位置 |
| --- | --- | --- |
| 航班 | 城市、机场/航站楼、班次、时长、票价来源、税费/行李已返回项和到达接驳 | 航司或授权 OTA |
| 铁路 | 准确车站、车次、席别、票价/余票核验状态、实名提示和到达接驳 | 12306 或授权渠道 |
| 酒店 | 位置、实景图、外宾资格核验状态、指定日期房态/房型/早餐/退改已返回项 | 授权 OTA 或酒店官方 |
| 餐饮与活动 | 地方特色、为什么适合、路线、营业/预约/排队、点菜/过敏/语言/支付 | 官方、商家或授权平台 |
| 市内交通 | 起终点、入口出口、步行、换乘、打车、行李和有来源的设施参考 | 高德等合规地图 |

当前开发阶段，购买、支付、自动退改和自动社交发布不在实现范围内；预订只准备跳转与确认记录。用户返回后可以记录“已订、已买、已确认”，后续规划以此为事实。

### 5. 行中 Today

旅行当天，移动端默认进入 Today，而不是完整编辑器。首屏只回答：

- 现在去哪里、什么时候出发；
- 从哪个入口、出口、机场、车站或航站楼开始；
- 建议交通方式、预计步行和换乘；
- 需要准备的票、证件、支付或双语现场表达；
- 一个低风险备选；
- 哪些设施、营业或路线信息不是实时的，需要现场确认。

移动端保留“对话、行程、地图”三个稳定入口，默认入口随阶段变化：未规划进入对话，已有方案进入行程，当天进入 Today 地图。完整来源和其他日期按需展开。

Today 应支持最小离线执行包：当天地点、路线摘要、酒店地址、已确认票务状态、双语现场短句和一个低风险备选。离线包必须显示核验时间和过期状态，默认遮盖预订号，且不得缓存证件、支付、Cookie、Token 或完整 Provider 响应。

### 6. 变化恢复

用户说“航班晚了两小时”“父亲今天走不了太多”“开始下雨”“这家店关门了”时，Agent 必须：

1. 保留已确认且不受影响的酒店、票务和地点；
2. 重新计算可用时间、移动成本和逐人负担；
3. 说明改了什么、为什么；
4. 给出一个可靠替代和一个下一步；
5. 在用户确认前不提交变化。

### 7. 到访数据闭环

只有已经加入旅行并完成到访确认的吃、住、玩地点才邀请反馈。产品优先询问推荐倾向、花费、等待、路线是否准确、同行人适配、语言/支付和设施变化；自由文字默认只用于个人回看与审核。

下一位旅行者只看到匿名结构化汇总。单条到访报告不能自动改写营业、价格、设施或外宾资格，只形成“近期有人报告、待核验”的线索。当前迭代不建设关注、点赞、公开 Feed、创作者激励或商家排名；是否引入由后续迭代依据到访闭环效果再评估。

## 出发准备：不是百科，而是这趟旅行的阻塞清单

准备检查只显示会影响当前行程的内容：入境与证件信息核对入口、手机网络与联系方式、支付和备用方式、外宾住宿、实名票务/预约、在中国境内可继续使用的登录方式。每项包含：

- 当前状态：已准备、待完成、临近出发复核或无法判断；
- 为什么会影响这趟旅行；
- 可信来源与核验时间；
- 用户下一步；
- 是否需要用户在外部平台完成。

产品不提供法律或签证结论，不收集完整证件和支付资料。国内模式自动跳过不相关的入境教育，只保留与具体旅行有关的票务、天气、路线和履约检查。

## 逐人适配与推荐理由

同行人的膝盖、体力、长辈、儿童、轮椅、婴儿车、过敏、饮食、作息和语言需求必须绑定到具体 Traveler，并实际改变住宿、路线、活动和餐饮。系统只保存行动结果，例如“父亲单段少走路、避免楼梯”，不保存诊断和病史；用户未给数字时不发明上限。多人偏好冲突时优先给出可解释的折中与轮换，只有共同安排明显伤害体验时才建议短时分组，并说明对时间、交通和安全的影响。

任何“适合你”“更在地”“少绕路”“少排队”“入境友好”的结论至少回答：

1. 有什么具体地方特征；
2. 为什么适合这次旅行和这些同行人；
3. 从住宿或上一站过去的时间与体力成本；
4. 预约、排队、点菜、实名、语言、支付或无障碍方面怎样完成；
5. 来源、核验时间和仍不确定的部分。

没有证据时显示待核验，不能用热度、标题、模型印象或商业报价推断适配。电梯、坡道、卫生间、储物柜和充电宝有资料时可以帮助判断，但必须标为非实时；“资料显示有”不能写成“当前正常运行”。

## 内容、地图与 Provider 分工

- 海外搜索、内容平台、OTA 和合作方负责让用户带着已有意图进入产品；分享链接与截图应直接进入对应旅行任务，而不是回到通用首页。
- 小红书、抖音、微信、大众点评/美团合作接口、运营资料和到访反馈负责发现长尾线索；发现层不能替代营业、路线、库存和资格核验。
- 高德和官方地图资料负责中国 POI、坐标、路线、入口出口与有记录的设施；12306、航司、景区、商家和政府页面负责规则；飞猪、途牛及其他授权 OTA 负责指定日期库存与报价。
- Agent 必须区分独立体验、同源转载、软广和商家自述，避免以内容数量制造虚假多数。
- Provider 缺失时可以形成部分结果，但必须指出缺口影响；静态 fixture、模型知识和旧缓存不能冒充实时接线。

## 跨端、账号与分发

全平台指**同一趟旅行连续可用**，不是每个平台复制同样多的功能：

| 入口 | 主要职责 |
| --- | --- |
| 海外 Web / H5 | 获客、免登录准备检查、链接/图片导入和主方案规划 |
| 桌面 Web / PWA / 壳 | 深度比较、地图路线、同行人协作与来源检查 |
| iOS / Android | Today、定位触发的路线查看、变化恢复、相机/语音与通知 |
| 微信 / 支付宝小程序 | 中国境内账号连续、服务跳转、轻量 Today 与分享回流 |
| MCP | AI 重度用户和合作产品嵌入同一 trip/decision/proposal/fulfillment 合同 |

Google、Apple、微信和支付宝登录继续保留，但首次价值之前不强制。上线时至少需要一种海外常用登录方式和一种在中国境内可继续使用的方式；账号绑定、合并和恢复必须经过真实平台授权，不能伪造成功。

## 商业闭环与成功指标

优先验证“合作方带客、用户使用”的 B2B2C 分发，B2C 单次旅行服务作为补充，透明跳转收入不得改变推荐排序。V2 不为验证商业闭环预建完整 B 端后台；只记录合作入口、激活旅行、有效跳转、行中回访和恢复结果。

北极星指标是**激活旅行**：用户获得一条可执行主方案，并完成至少一次保存、分享、导航或可信预订跳转。聊天轮数、候选数量、页面停留和下载量不能单独代表价值。

关键漏斗：

1. 进入产品 → 免登录完成首次输入；
2. 首次输入 → 看懂准备缺口和路线骨架；
3. 第一份结果 → 完成一个真实下一步；
4. 行前规划 → 旅行当天再次打开 Today；
5. 发生变化 → 接受一次局部恢复；
6. 完成到访 → 留下一条结构化结果。

质量底线包括：不得伪造动态事实；不得把缺路线的地点列表称为行程；敏感信息不得进入模型和日志；用户确认前不得购买或提交变化；商业合作不得改变适配排序。

## V2 完成标准

V2 只有在以下真实用户场景通过后才可称为完成，合同测试或静态页面不能替代：

1. **美国情侣首次来华：** 免登录用英文输入上海四日旅行，得到本次准备缺口、地图路线骨架、外宾住宿核验和一个可信执行动作；登录后无损保存。
2. **新加坡家庭带父母：** 每个人的体力与设施要求分别保存，并实际改变住宿、路线、交通和日程；方案回显预算与体力取舍。
3. **德国商务延伸旅行：** 固定工作时间后生成两日当地体验，能从机场/车站接到酒店和活动，并提供双语现场表达。
4. **复游美食旅行者：** 导入一个视频或分享链接，地点经过实体归一、地图定位、路线代价和营业/预约核验后进入主方案，而不是只生成摘要。
5. **行中 Today：** 手机上能在三次点击内看见当前路线、入口出口、下一步、所需票证和一个备选；非实时设施清楚标注。
6. **延误与闭店：** 航班延误和餐厅闭店同时发生时，只调整受影响部分，保留已确认酒店和无关活动，用户确认后才提交。
7. **国内用户：** 同一内核完成吃住行玩联动、地图和长尾发现，首屏不出现无关的入境准备教育。
8. **Provider 缺口：** 高德、库存或社交来源不可用时，界面显示具体影响与恢复动作，不生成假地点、假路线、假房态或假票价。
9. **地图工作台：** 第一视口内出现真实旅行内容或地图；用户能区分候选、路线骨架、Day Timeline 和已确认/已预订，准备卡不能把旅行推到第二屏。
10. **变化预览：** 换住宿或拖动地点先显示路线、预算、同行人、锁定和未知项影响，用户确认后才提交。
11. **离线 Today：** 移动端断网时仍可读取当天关键执行资料，且不会暴露证件、支付或未遮盖预订号。

本文先锁定产品结果。后续按以下顺序同步，不同时重写全部系统：

1. 更新界面与路线规范：匿名首页、第一份结果、地图工作区、Today、详情抽屉与语言体验；

本文随用户决策持续修订；文档之间冲突时以最新用户决策为准并同步修订相关文档。代码能力以真实入口、运行结果和测试证据为准，不能因 PRD 已更新而声称 V2 已实现。

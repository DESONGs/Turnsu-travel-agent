# 持续规划：上下文、Parent 与 Jev 交接

更新：2026-09-22。状态：**用户确认与业务模型一并重设计；本次仅形成开发规范，尚未实现或完成模型验收。**

与 [14 业务模型](./14-continuous-planning-business-model.md)共同实施。业务状态回答“现在保存了什么”，本文回答“模型这一步实际看见什么、如何理解变化、结果交给谁继续”。执行任务不能只改其中一份合同。

## 1. 当前缺口与目标

现有原生 Pi 会话会在模型调用前重读 Trip 事实，也有独立 Child、Jev 快照、工具结果与 continuation；这些能力保留。缺口在于目标、工作草案、决策依据、问题、相关变化和完成回执仍分散，没有作为同一规划过程交接。

当前 Jev 快照主要包含本批候选、brief、同行人、锁定及天气；模板主要是偏好支持与评分。它不能仅凭这些内容可靠处理“新要求如何影响原计划及下一步”。需要按具体问题给上下文，不能把候选评分直接当完整规划完成。

目标是每轮模型都能明确：

1. 用户原本要完成什么，本轮改变了什么；
2. 当前已采用版与工作草案各是什么；
3. 哪些决定有有效依据、哪些只是模型假设；
4. 哪些工作已完成，哪些问题阻塞下一步；
5. 本轮允许处理的范围、工具、预算与授权；
6. 结果需要交回哪个问题，生效依赖是什么。

## 2. 信息层级与权威

| 层 | 内容 | 规则 |
| --- | --- | --- |
| 固定合同 | 角色、受限工具、隐私、来源与提交权限 | 与任务数据分开；来源文本无权修改 |
| 当前权威状态 | 目标、要求、授权、已采用版/草案、有效报告、未解决问题 | 每轮生成一致的版本快照 |
| 本轮任务材料 | 变化、相关候选与证据、到访邻域、具体问题和完成条件 | 可按任务裁剪；不得丢决定所依赖的事实 |
| 历史与回执 | 用户纠正顺序、简短决定摘要、已完成工具回执、相关对话 | 辅助理解与去重，不能覆盖最新权威状态 |

“最新”只解决同一事实的版本问题，不会提升信息权限。用户陈述、来源事实、模型假设、未知和冲突分别标记。Provider 文本、图片文字与历史模型回复均不能成为指令或采用授权。

用户原话及纠正顺序仍是语义理解依据，不能先用关键词过滤掉否定、数值、范围或专名。结构化状态存在疑义时回读原话；只在仍会改变产品结果的歧义上询问。

## 3. 每次模型调用的上下文合同

扩展现有 Context Pack / JudgmentSnapshot，避免新建上下文真相库。以下字段按现有类型映射：

    basis:
      tripId, planningId, objectiveVersion
      planId, planVersion, snapshotId, dependencyFingerprint
    goal:
      originalRequestRef, currentObjective, changeRequest, completionCriteria
    boundaries:
      requirements, locks, authorization, allowedChanges
    plan:
      adoptedSummary, workingDraft, relevantVisits, globalConstraints
    decisions:
      relevantChoices, briefReasons, evidenceRefs, assumptions
    issues:
      issueId, affectedVisits, missingFacts, resolutionOwner, completionCondition
    inputs:
      candidates, evidenceExcerpts, sourceVersions, unknowns
    progress:
      completedReceipts, pendingStep, previousFailure, remainingBudget, deadline
    delta:
      changedFacts, invalidatedResults, stillValidResults

不要在每个 Agent 中复制整份对象。它是一份权威状态的不同受限投影，完整记录留在业务/执行存储。

- Parent 始终知道目标、全部硬约束、授权与总体进度；操作某一段时得到具体到访和相邻依赖。完整规划拿到所需完整到访结构；不能只给几个地点名称。
- 全局预算、日期、已预订/固定锚点以及相关逐人硬要求不能因“只处理晚餐”而被遗漏。
- 同一轮组装必须来自一致版本。组装后若发生变更，调用结果按依赖复验；不能把不同读取时刻的字段拼成一个声称原子的快照。
- 每次有业务工具改变了事实/计划，都向下一次模型调用提供新的权威快照和变化说明。不能只在会话开始时嵌入一次草案。
- storageVersion 用于存储并发，不直接代表语义变化；依赖指纹以稳定序列化的业务字段生成，不受 JSONB 键顺序影响。

## 4. Parent、Jev 和 Child 分别拿什么

| 执行者 | 必要输入 | 输出与权限 |
| --- | --- | --- |
| Parent | 当前目标、约束、采用/草案状态、变化、候选和证据、问题与完成回执 | 开放规划、问题分解、变更提议和用户解释；通过唯一业务工具提交 |
| Jev | 一个或一批独立问题；对应到访、备选、逐维证据、相关约束及版本 | 有依据的支持/冲突/未知、分数和置信度；不生成外部事实、不执行工具、不授予权限 |
| 现有 Child | lane 的任务、同源快照的相关部分、允许读取的候选/证据及完成条件 | 只读分析和结构化建议；无 Provider/业务写/递归委派权限 |
| Checker | 合并后的完整计划、有效事实、费用和路线输入 | 确定性检查报告及受影响范围；不替 Parent 重新创造行程 |

同一问题可拆为设施证据支持、偏好比较等独立判断；带前后依赖的问题分阶段执行。例如先验证候选事实，再比较合格替代，最后核验组合计划。不同 Agent 不共享可变聊天窗口，不能靠拼接多段聊天当作 Join。

Jev 的现有偏好模板保留其已验证边界。新增“变化影响”“具体问题支持”等模板须独立校准；没有验证前只记录或交由 Parent 审阅，不能依据自报高置信度自动改草案。

## 5. 交接结果必须可消费

在现有工具回执中补齐必要字段，保持业务语义一致：

    identity: operationId, issueId, snapshotId, templateVersion
    basis: planVersion, dependencyFingerprint
    outcome: completed | partial | waiting | conflict | failed
    businessStatus: 精确业务结果，例如 input_rejected 或 trial_ready
    observations: 来源事实、未知、冲突及证据引用
    proposedChanges: 明确的草案变更；只读工具为空
    validation: 通过/未通过项及相关到访
    persisted: 实际保存的版本和操作回执
    continuation: 已解决事项、未解决事项、可执行下一步或等待条件

各字段的最终类型复用原合同；不建立一套与现有结果重复竞争的状态系统。外层任务完成、模型调用完成、路线核验通过、草案可采用分别映射，不得互相替代。

结果消费遵循：

1. 核查用户/Trip、操作身份、当前取消状态、快照和依赖。
2. 接受仍适用的结果，关联到原问题；在允许范围内更新事实、判断或草案。
3. 持久化语义操作回执及下一步，再接续 Pi。
4. 发生依赖冲突时返回变化与可复用部分，Parent 基于新材料处理原问题。

例如工具返回旧候选引用时，应包含失效引用、当前可用引用、失效原因与读取入口；只有身份可证明相同才附旧新映射。不能让 Parent 通过多次报错猜随机新 ID。

## 6. 原生上下文压缩与容量管理

继续使用 Pi 原生 AgentSession、工具消息配对、checkpoint 与 compaction；不维护第二套会话系统。

- 当前权威状态单独投影，不能由历史摘要替代。摘要保留用户目标、纠正、决定依据、未完成问题和回执索引。
- 摘要或上下文中模型曾经提出的假设仍标记为假设；重复出现不会升级为用户事实。
- 旧工具快照只在明确覆盖同一对象、范围和版本关系时收缩为回执。某次餐饮查询不能覆盖之前酒店查询；部分草案不能挤掉唯一完整计划。
- 进行中/延后工具保留完整参数、调用 ID 和相配回执；恢复先补齐工具结果再继续，不能留下孤立工具消息。
- 当前模型有效窗口、输出预留、系统与工具合同、账号输入预算共同决定输入容量。保留当前限制，不通过扩大窗口或总预算掩盖业务循环。
- 首先删除重复快照、压缩历史叙述、按相关性取证据正文；保持来源、版本与未知项。选中、锁定、用户点名和当前问题引用的到访/候选优先保留。
- 完整行程不能因为 fixed limit 只保留前若干站；过大时按日/依赖邻域分阶段，Parent 始终拥有总体目标、锚点和摘要，提交时完整核验。
- 必要受保护输入仍超限时明确报告并分阶段处理；不能截断 JSON 或悄悄丢掉硬约束。

只取相关证据的方式复用现有受限读取工具，无需为本轮新增向量数据库。Jev 的字节输入上限与 Parent 的 token 上限分别核算，不能互相代替。

## 7. 多端变化和缓存适用性

读写依赖由业务代码根据工具类型、到访、时间和约束确定；模型可增加依赖但不能删除必查项。

例：模型正在替换晚餐，另一端增加一位同行人。保存新事实后，偏好证据可能继续有效，但餐饮总价、房间和车辆容量需要复核。晚餐结果返回时，代码确认其依赖；保留可复用判断，将受影响问题送回 Parent，而不是整体覆盖新状态或全部从头研究。

缓存隔离至少包含用户/Trip、任务或问题、相关计划/候选/事实版本、来源时效、模板、模型和校准版本。相同问题的失败结果不能作为成功缓存；无关变化不应强制重算全部判断。

首次实施可采取保守依赖失效，但必须保留已保存成果并返回具体影响；只有证明依赖完备后才开放更细粒度复用。不能为减少调用而漏检跨域依赖。

## 8. 持久接续与停止条件

持久化的 continuation 保留当前目标和问题、步骤状态、basis、已完成回执、待处理工具、预算和原截止时间。进程内 Map 不能是唯一拥有者。

- 恢复先读取当前业务状态，再验证保存结果的适用性；有效步骤不重复执行。
- 用户回答绑定问题和依赖；保存后继续该问题。模型在后续失败时，回答及草案仍可读取。
- 额度等待使用既有 queued/notBefore，释放 Worker，不要求用户点击继续。
- 取消立即阻止迟到提交；结果不明的写入沿用中断保护，先查回执。
- 没有新参数、证据或条件变化的相同失败不能反复重试；时间和修复上限不能被新 snapshotId/runId 重置。
- 资料未知可保存部分结果；明确需要用户事实才等待回答。暂时不可查询与实际约束无解分开，不把来源失败写成用户必须放宽要求。
- 一次修复上限约束业务重排，不把必要读取、参数纠错或最终解释强行截断。遵循 [14](./14-continuous-planning-business-model.md) 的规划轮次与期限语义。

## 9. Jev 调度与产品表达

固定 jev-1.13.0，保留 off / shadow / auto。同快照独立问题合批，依赖问题顺序执行；只重算受影响部分。规则能完成的操作不调用 Jev。

沿用已确认账号约束：正常 1,080 RPM、重试最多 60 RPM、保留 60 RPM 余量；全部请求任意连续 60 秒不超过 1,200。同时检查 TPS、输入预算、账号冷却和在途限制，使用 PostgreSQL 原子预留及数据库时间；同 Trip 最多一个 Jev 请求在途。保持用户公平与短交互/续算 2:1、空闲互借。

用户只需要看到实际变化、还缺什么和必要下一步。关键状态、金额、时间与单位来自服务端视图；Parent 可自然解释取舍，但不能从“工具结束”或“模式偏好”推断“已核验”。变化摘要直接可见，内部推理、快照和调度细节不展示。

## 10. 实施与验收

主要改动面：原生会话的 current facts / compaction、Parent digest/工具回执/续接、travel-judgment 快照和模板、现有 Child Context Pack、execution continuation，以及共享业务视图。

业务合同、工具 schema、上下文构建、提示词和 Skill 必须同步适配；不能先让 Prompt 声称新字段已存在。沿用用户确认边界，对 agent.md、.pi/SYSTEM.md 和相关 Skill 只做本次合同必需的最小同步。

与 [14](./14-continuous-planning-business-model.md) 的同一黄金路径一起验收，特别检查：模型切换、摘要后恢复、长计划跨阶段、否定与纠正、多端更新、过期答案、Jev 分歧/高置信错误、资料失败和迟到结果。

测量首个有用结果、完整草案时间、用户打断次数、重复读取/无进展调用、状态偏差、模型成本及上下文大小。固定场景比较当前基线与新方案；真实接口、受控依赖、浏览器和容量结果分别报告。完整清单见[开发交接](../research/2026-09-22-continuous-planning-redesign-handoff.md)。

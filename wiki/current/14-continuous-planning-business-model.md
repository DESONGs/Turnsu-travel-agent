# 持续规划：业务模型与执行联动

更新：2026-09-22。状态：**用户确认重设计方向，作为下一轮开发依据；本次只更新 Wiki，尚未实现或验收。**

配套：[15 上下文与模型交接](./15-model-context-and-handoff.md)定义同一业务过程的模型输入输出；[开发交接与验收](../research/2026-09-22-continuous-planning-redesign-handoff.md)记录证据、顺序及尚未通过项。本文与 15 对冲突的旧方案具有优先级，不能据此把旧实现标为已完成。

## 1. 用户结果与设计边界

目标路径：用户表达要求 → 自动研究与比较 → 保存可查看的草案 → 核验并局部修正 → 必要时问一个问题 → 回答后接续 → 用户采用。

用户补充要求、来源变化或模型失败后，系统仍知道原目标、已确认安排、有效判断、未解决问题及下一步。吃住行玩在同一计划中相互约束；不能退回各域独立生成后拼接。

沿用原生 Pi Parent、TravelService / Trip Runtime、PostgreSQL、Worker、现有 execution repository 和客户端。业务状态仍只有一个权威提交入口。新增内容先作为同一 TripState 内的明确字段和严格 TypeScript 合同；不新增状态服务、消息总线或通用工作流框架。

关键修正：长期用户成果、可失效的证明、临时提交命令具有不同生命周期。Proposal 与预览缓存可以过期，但不能成为用户计划的唯一载体。

## 2. 业务模型

以下名称表达职责，落地时优先复用现有类型；不是要求建立同名服务或数据表。

| 内容 | 业务含义与必要字段 | 权威位置 |
| --- | --- | --- |
| 规划目标 | 当前目标、受托范围、成功条件、用户输入顺序、目标版本；新输入是补充、纠正、局部修改还是取消 | TripState；原始可保存输入继续在会话/请求记录 |
| 要求与授权 | 逐人要求、偏好、日期、预算、锁定项；明确用户事实与模型假设；授权绑定动作和范围 | TripState |
| 候选与证据 | 稳定业务身份、选项条件、资料版本、来源、时间、未知与冲突 | TripState 既有候选/证据结构 |
| 持久计划 | 已采用版本、当前工作草案；具体到访、站序、时间、用途、来源与费用依据；版本及前版引用 | TripState 的明确计划结构 |
| 决定与问题 | 选择的简短理由和依赖；尚缺事实/证据/取舍；影响哪些到访、由谁解决、下一行动与完成条件 | TripState 的有界决定与问题记录 |
| 执行进展 | 当前请求、步骤、快照引用、工具回执、已完成工作、等待原因、期限、预算及取消状态 | 现有 execution repository |

上下文和客户端视图由这些权威内容投影生成，不再另存可独立修改的模型事实副本。只保存可核对的决策摘要，不保存模型隐藏思考；不得把模型理由当作事实证据。

### 2.1 稳定身份

- 地点、可选报价和一次到访必须可区分。同一家酒店上午寄存、晚上入住是两个到访；同一餐厅午餐、晚餐也是两个到访。
- 完善现有 stopId：创建一次到访后保持稳定，不由数组位置或排序重算。用餐用途显式记录，不能依赖候选默认时段反推。
- 候选刷新更新资料版本；确定是同一业务选项时保留其身份。不同房型、日期或票种不得因地点相同而误合并。身份无法确认时新增候选并保留旧引用，不让模型猜替换关系。
- planId / planVersion 表达计划身份；execution runId 表达一次执行。规划任务不能以一个进程内分析 run 的存活作为存在条件。

### 2.2 两组互不替代的状态

计划生命周期描述草案、已采用、已替代或用户放弃；核验状态描述待检查、通过、有冲突、资料未知或过期。已采用版本可以因新事实变成待重新核验，但仍是用户此前采用的版本。

费用报告绑定计划版本和人数、房晚、餐次、票种、路线及价格版本。新报价失效时保留“上次估算/时间/缺口”，不能静默回退为另一套分域粗估；未知费用不按零元计算。

## 3. Parent、Jev 与代码的连续责任链

1. 服务端接收并按顺序保存用户输入；Parent 解释目标和变化，结构化保存事实、范围与明确授权。
2. 从当前计划和未解决问题形成下一步。Parent 负责开放组合与取舍；确定性计算、已有有效读取可直接复用。
3. Jev 对同一快照上的独立小问题合批判断，返回支持、冲突、未知、证据及置信度。新问题模板先校准，未校准不得自动推进。
4. 查询、判断、核验结果进入原问题及依赖版本；它们必须实际影响候选、草案或下一行动，不能只留下评分。
5. Parent 根据结果提出具体计划变更；Runtime 检查、合并、保存草案，再核验整体可行性。
6. 仍有可执行的必要步骤就接续；等待用户、来源或配额时保存进展。交付说明来自实际保存的结果。

这不是“研究、评分、排程”只能各运行一次的固定流水线。问题决定下一步；预算和执行限制仍有界，不能以模型持续输出冒充持续进展。

| 情况 | 默认推进 |
| --- | --- |
| 确定性操作或有效结果可复用 | 直接处理，零 Jev 调用 |
| 已有证据足够，属于校准通过的可撤销偏好判断 | Jev 判断后经规则检查更新草案，继续核验 |
| 资料可查但缺失 | 自动定向补查，不向用户转嫁设施核实责任 |
| 可在既定要求内解决的冲突 | Parent 提出局部调整，保留未涉及安排 |
| 只缺用户专属事实或必须改变重要约束 | 一个有影响说明的问题；用户回答后自动接续 |
| 资料服务不可用或期限到达 | 保存部分成果和确切缺口；可恢复等待释放 Worker |
| 已有明确采用授权且结果仍在其范围内 | 通过完整检查后提交，不重复确认；授权不能由置信度推导 |

## 4. 工具合同按业务写面区分

| 工具语义 | 允许改变 | 必须保留 |
| --- | --- | --- |
| 保存要求 | 用户明确变化的事实、目标与授权；标记影响范围 | 已保存计划及未涉及要求 |
| 查询/刷新资料 | 指定范围的候选、证据与新鲜度 | 已采用计划、其他领域候选 |
| 核验计划 | 指定计划版本的路线、时间、费用与适配报告 | 站序、时间、餐次与到访用途 |
| 修改草案 | 明确的新增、替换、移动、调整、删除到访 | 未涉及安排、锁定项、原已采用版本 |
| 采用 | 已检查版本、选择与采用记录的一次原子提交 | 不受本次授权影响的业务内容 |
| 放弃/撤回 | 对应草案或明确授权的采用变更 | 候选、原方案和其他请求成果 |

首次计划可提交整份草案。后续调整优先以稳定 stopId 的变更提交，服务端合并未变部分。大范围重排必须声明范围，校验完整性和保留项，不让“未在新 JSON 出现”隐式表示删除。

路线刷新只对保存的到访时间线核验。若核验建议移动时间，应返回问题及调整建议，由修改草案合同接手；来源不可用不能把计划时间写成 null。

## 5. 依赖变化与局部更新

采用有限、可测试的业务依赖规则，无需通用依赖图平台。

| 变化 | 需要检查的典型依赖 | 不应自动删除的内容 |
| --- | --- | --- |
| 总预算 | 预算符合性、当前选择的取舍 | 站序、候选、有效路线 |
| 人数/房间数 | 餐饮、门票、住宿、车辆容量及费用 | 与人数无关的地点事实 |
| 无障碍要求 | 场所通路、上下车、路线连续性、相关时间 | 已采用时间线和未受影响决定 |
| 抵达信息 | 抵达锚点、首段接驳及实际受影响后续衔接 | 原版行程；形成新草案后再处理调整 |
| 日期/目的地 | 日期覆盖、库存、营业、天气、路线及计划适用性 | 历史已采用版；不得展示为新条件下仍有效 |
| 局部候选/报价 | 引用该选项的判断、费用及相邻路段 | 其他领域的可靠候选 |
| 天气 | 与变动风险有关的户外安排、路线及备选 | 无关候选与保存的草案 |

更新事实时保留计划，标记需要复核的报告/问题。历史陈旧结果可供比较但不再支持当前采用。

候选刷新先在工作副本上完成合并与校验，再原子提交。重建未受影响候选失败时，保留原状态并返回可恢复错误；不得保存“先删旧、后保留失败”的中间状态。empty_verified 只描述本次查询范围，没有扩大删除范围的含义。

## 6. 并发、提交与恢复

- storageVersion 继续用于 PostgreSQL 并发保护。结果另携带计划版本及代码确定的相关依赖指纹；模型声称的 readSet 只能补充，不能缩小服务端检查范围。
- 模型调用和 Provider 查询在事务外；提交事务内复验租约/fence、取消、版本、授权、锁定及整体约束。业务变更、操作回执和相应事件必须保持可核对的一致性。
- 同 Trip 的提交继续串行受控。无关事实变化允许代码证明结果仍适用；依赖冲突返回当前版本、变化范围、可复用结果和下一步，由 Parent 接续，不盲目改 revision。
- 同一语义操作的重复提交返回原回执。结果不明的写入先查询回执/提交记录，不能凭模型回忆重放。
- 进程内 Coordinator 只做即时协调；长期步骤、修复状态、预算与期限在现有 execution repository。重启不得重新获得未用过的修复额度。
- 同一需求版本的一轮业务修复沿用一次上限；参数格式纠错和必要读取不计业务修复。换 runId、补查或恢复不重置限额。用户实质改变目标/要求时显式形成新的规划轮次并继承已有成果。
- 总期限首次入队确定，等待与恢复不重置。已结束任务由用户发起新请求时可形成新执行期限，但不能将旧任务伪装成仍在自动重试。
- 重复的失败若没有参数、事实或来源状态变化，不重复调用同一工具；交付具体缺口。不要用强行终止 Parent 取代有意义的补查、调整和解释。

## 7. 问题、回答与跨端

问题绑定具体未解决事项、用户/Trip、稳定选项 ID 和相关依赖。保留现有 answerTo 入口；逐步以具体依赖替代“任一 revision 变化都让所有问题过期”。

回答与消费记录幂等保存，再驱动原问题的后续步骤。后续模型失败不撤销已保存回答、不删除草案。另一端已经解决或替换的问题必须撤下；旧选项不得覆盖新决定。没有影响该问题的背景读取不应让它失效。

各端使用同一服务端视图，分别展示计划生命周期、核验状态及执行进度。工具结束不能映射为路线已核验；默认候选时间不能作为已采用日程。核心变化、未解决缺口与必要操作直接可见，内部运行标识不进入用户话术。

## 8. 黄金路径

已采用一天行程后，用户补充“增加一位轮椅使用者，原安排尽量保留”：

1. 保存人数/需求变化；原计划保持完整，相关核验变为待更新。
2. 形成酒店入口、两处景点、餐饮与接驳的具体问题；自动取得可查询资料。
3. Jev 只判断提供的证据对问题的支持、冲突或未知；Parent 比较替代，代码计算费用和路线。
4. 原景点不满足时提出局部替换草案，保留午餐、晚餐用途和其他安排；整体检查时间、餐次、预算和无障碍连续性。
5. 没有可靠证据时保存部分草案及缺口；必须放宽重要要求才提问。回答后从对应问题继续。
6. 用户采用授权存在且全部必要检查通过才提交；刷新和换端仍看到相同版本及核验状态。

## 9. 迁移与开发责任

- contracts / core / Trip Runtime：严格 TypeScript 的计划、到访、变更、问题、依赖与核验规则。
- TravelService：复用现有公开入口，组织 Provider、业务规则、事务和统一视图；不另建第二套业务语义。
- execution repository / Worker：持久步骤、回执、原生 checkpoint、预算/期限和恢复。
- Parent / Jev / Child：按 [15](./15-model-context-and-handoff.md) 消费同一版本事实与结果。
- Web、桌面及受影响小程序：使用统一业务状态，不能自行重建计划。

从旧 mobility.itinerary 与 proposal.itineraryPlan 迁移可核对的计划；预览只能提供辅助快照。旧数据已经缺失时仅从可信保存记录恢复，不从默认时段或模型回忆补造。迁移幂等；切换后新模型为唯一业务写源，旧字段若保留只能是兼容投影，不能双向维护。

## 1. 用户方向与完成结果

用户满意现有地图，对路书形成、行程规划，尤其交通方式不满意。要求吸收参考项目的业务方法，形成清晰、可维护的实现，再以真实用户流程 QA。地图展示与交互保留，必要的信息入口完善沿用现有组件，不启动地图重设计。

本轮目标：**旅行者能理解每天为何这样安排、怎样到达、什么时候必须出发、花费包含什么，且遇到变化后能继续。**

黄金路径：一句旅行需求 → 保存范围与必要事实 → 自动比较来源与可行选择 → 形成完整交通链和每日草案 → 核验并局部修正 → 仅必要时问一个关键问题 → 回答自动接续 → 用户采用 → 刷新/跨端保留 → 行中变化后只调整相关部分。

用户可见的完成证据：

- 每天的重点、固定安排、用餐/休息、住宿及移动连贯；主线之外的可选项不挤占核心时间。
- 去程、当地移动、跨城转场与返程按请求范围完整衔接；自行安排有明确边界。
- 每段能说明起终点、方式、建议出发时间、预计抵达、办理/换乘余量、费用依据、来源与待核验事项。
- 主要方案默认清楚，只有实质取舍才展示少量替代；普通用户无需先替 Agent 逐域选候选。
- 缺数据、超时和回答后接续都保留已有成果；助手描述、工作台、数据库状态一致。

保留单一 TripState、Parent 提交权、权限/锁定、PostgreSQL、Worker、现有 execution repository 与跨端业务服务。14/15 的计划与证明分离、相关变化失效、原生会话恢复继续有效；本文补充旅行/交通业务语义，不撤销这些要求。

## 2. 业务范围与必需合同

以下是必须解决的业务问题，不要求建立同名新服务。

| 编号 | 范围 | 必须表达和验证的结果 |
| --- | --- | --- |
| B01 | 完整交通链 | 出发端接驳、大交通、抵达端接驳、当地移动、必要转场、返程；范围由用户目标决定。已订班次与未订建议区别处理，不能将模型挑选的早班当不可更改事实 |
| B02 | 多方式比较 | 比较有意义的路线差异，以及人数、行李、步行、换乘、时间和费用；支持用户已表达的方式偏好。实际选中方式、解释、审计和地图一致 |
| B03 | 时间衔接 | 区分移动、进出站、办理、等候和余量，避免重复计入 Provider 已包含部分；检查班次/运营日、停止办理/检票、末班与预约期限。阈值有依据或明确为假设，未知不能伪装成已核实 |
| B04 | 自驾/租车 | 区别驾车与打车；必要时包含车辆人数/行李适配、取还车地点/时间、停车点、停车后步行、收费和限制。不能忽略车留在上一地点的连续性；无来源部分明确标出 |
| B05 | 景区内部移动 | 区别景区入口、换乘点与实际游览点；按实际范围核对接驳车/索道/轮渡等运营、末班、票价包含项与返回路径。对不涉及景交的城市路线不增加无关步骤 |
| B06 | 每日质量 | 在硬约束成立后比较绕路、赶路占比、活动密度、累计步行与休息。尊重实际作息和不同同行人；覆盖在行程时间内需要的餐次，可为酒店早餐/自行解决，不强制新增餐厅 |
| B07 | 全程费用 | 价格绑定日期、人数、席别/房型、车辆数、包含项与来源；区分每人/每车/每房晚/单程等单位，避免联票重复收费；已知、估算、未知分别汇总 |
| B08 | 变化与备选 | 备选绑定触发条件和影响：晚到、取消、天气、排队或交通停运等；只重算受影响范围。保留原计划及比较依据，不能删除限制使核验变绿 |
| B09 | 可执行路书 | 在现有每日行程/路线详情中呈现主线、衔接、费用、提醒和恢复动作；需要时再展开来源和候选。Today 从同一计划投影，不维护第二份文本事实 |

完整往返、多城、自驾和景交在本轮范围内按依赖顺序实施，不能仅完成到站后市内路线就宣布本轮结束。缺少真实来源时可先完成合同与显式模拟流程验证，但对应真实能力标记未通过；不得靠模型生成车次、站内设施或道路填空。

不增加自动购买、退改签或外部发布能力。预订延续现有交接与用户确认；用户提供的已订信息只保存非敏感旅行事实。对方的默认作息、内容创作偏好和静态规则不覆盖本项目用户。

## 3. 自动推进和用户交互

| 情况 | 默认动作 | 何时才需要用户 |
| --- | --- | --- |
| 有效事实、确定性计算、只保存预算 | 直接完成对应操作，保留未涉及计划；不重新规划，不额外请求语义判断 | 原要求不明确且会改变结果 |
| 来源可补查 | 按缺口定向查询，保存来源、时间、未知或冲突 | 需要用户独有材料；不能让用户替系统核实公开资料 |
| 多个方案都满足要求 | 自动选合理主方案，说明实际取舍；现有选择接近时优先稳定 | 有重大且无法从偏好决定的取舍 |
| 局部冲突有约束内修复 | Parent 调整相关段，代码重新检查受影响范围与全局约束 | 必须改变已锁定/已订安排、重要预算/日期/硬要求 |
| 缺个人事实 | 保存条件性草案和一个有选项影响的问题 | 例如是否接受夜车、必须返程时间、特殊行李与车型需求 |
| Provider/模型/配额暂时不可用 | 显示准确缺口，保留成果；复用现有持久等待/恢复 | 只有真正需要用户选择下一方向时，不要求反复点继续 |
| 结果可采用 | 按既有采用授权与全局检查提交，解释实际变化 | 无采用授权时用既有确认入口；不由模型置信度产生授权 |

问题继续用稳定 ID、answerTo、依赖版本和幂等消费。取消、另端新决定或条件变化后的迟到结果不能提交。外部普通未知项与硬约束冲突分开处理：未知报价/未来天气不应一概阻断草案；缺少赶车必要条件或连续无障碍证明，不能伪称可执行。

主线程须明确“保存草案、采用计划、出行前仍需核验”的可见状态及各自条件。不要以全局禁用按钮替代补查、可行替代和下一步，也不能将 blocking 降成 warning 来取得通过。

## 4. 主线程先完成的技术审查

开发已获授权。常规、可逆且不改变核心产品边界的技术选择自行决定；只有新证据要求重大改变目标/架构或新增外部权限时再向用户说明。审查结果简要回填本节，再实施，不把本文变成另一次等待批准的阶段。

### 4.1 必须回答的五个问题

1. **现有节点、到访、报价和路线怎么扩展？** 交通商品/班次、一次实际乘坐、一次地点到访的身份不同。明确复用哪些字段、哪些必须增加，如何保持稳定 ID 与旧数据回读；不能把大交通到达节点复制成返程后就假定语义成立。
2. **谁选择，谁核算，谁提交？** Parent 做开放组合与取舍；Provider 返回来源事实；严格 TypeScript 负责衔接、计价、约束及可采用条件；TravelService/Runtime 唯一提交。Provider 中影响产品决策的默认阈值应接受审查，不能散落在 Adapter、Prompt 与前端三处。
3. **如何表示实际路线和完整耗时？** 一个方式可能有多个备选，选中身份不能只有 mode。耗时分项注明来源覆盖范围；门到门、站到站、景区入口到游览点不可混算。保留已有道路几何和坐标体系。
4. **变化影响如何计算与恢复？** 修改预算、酒店、班次、停车点分别影响哪些段/报告；怎样保留原版与无关安排；等待/重启怎样从回执接续而不是重复查询或提交。
5. **怎样控制规模和时延？** 有意义的备选、查询缓存、受影响范围和独立读取并行均受既有执行预算约束。避免全候选全排列与反复规划整趟；独立读取可以并行，但不能用更多 Agent 掩盖缺失业务规则。

### 4.2 建议沿用的责任分布

2026-09-30 主线程接手决定：复用 `DecisionNode` 表示有来源的交通商品，`ItineraryPlanStop.stopId` 表示一次实际乘坐或到访；班次的出发端和抵达端分别用于前后接驳，返程必须来自独立方向/日期查询。扩展现有到访角色和 `operability` 中经严格 TypeScript 校验的交通资料，不建立新状态源。`MobilityLeg` 的选择改为稳定备选 ID，mode 保留兼容；来源时长与办理/等候/余量分开，费用携带计价单位和包含项。Parent 选择，代码核算及指出缺口，TravelService/Runtime 提交，现有地图只读同一投影。

预算变化只重核费用符合性；班次/地点/车辆变化重核相关接驳和全局衔接，原采用版保留。旧状态缺少交通明细时按未知投影，不能反推已核实往返；新增字段可选、已有计划幂等回读。实施先修现有失败回归，再贯通往返、自驾/景交与每日展示；以 T01–T12、PostgreSQL 回读和浏览器交付验证，真实来源覆盖独立记录。

| 模块 | 建议调整 | 不应承担的职责 |
| --- | --- | --- |
| `contracts/`、`core/` | 扩展交通/到访/费用/核验合同和确定性规则；为旧状态做可验证的增量兼容 | 凭常识编造班次/设施；新建独立事实库 |
| `src/providers/` | 按所需方向、日期与地点查询；保留有差异的路线、报价条件、时效和冲突 | 静默替用户放宽约束或提交计划 |
| Parent 与现有 Skills | 组织主线、提议局部变化、解释真实取舍；工具失败后处理未完成业务 | 用自然语言覆盖持久计划、虚构已执行动作 |
| Jev / Child | 对明确问题和受限快照做独立判断，带依赖交接 | 共享可变上下文、决定购买、授予采用权限或替代全局检查 |
| TravelService / Runtime | 合并与校验草案、关联证据/问题、原子提交、保护取消与幂等 | 在不同客户端复制业务规则 |
| execution repository / Worker | 沿用持久步骤、截止时间、预算、配额等待与原生 Pi 接续 | 另建队列/常驻规划服务，或恢复时重置额度 |
| 现有前端与地图投影 | 呈现主方案、交通选择、日程、影响与恢复入口；已选方式与地图一致 | 计算第二套事实路线或默认自改计划 |

这些是责任建议，不强制新建同名文件、引擎或服务。优先扩展现有模块；新增抽象必须能指出它解决的具体验收案例。

### 4.3 模型上下文与工具调整

复用 15 的版本化快照，针对交通任务补齐：本次目标/变化、计划与当前段、前后固定锚点、相关同行人/行李要求、允许方式、报价条件、全局预算、已知来源/有效期、未知项、采用授权以及已完成工具回执。

Parent 始终保有全局硬约束；局部 Child/Jev 只拿判断所需材料。比如“这个换乘能否成立”必须带前段实际到达条件、后段办理截止、站点关系和证据，不能只给两个交通名称。输出必须包含适用依赖、结论、来源支持/缺口和下一动作，并由主流程消费。

算术、期限比较、缓存命中与明确保存操作零 Jev 调用。未校准的新语义模板先 off/shadow；不得为了本轮交通能力扩大自动放行范围。既有 Jev 账号预算仍按正常 1,080 RPM、重试最多 60 RPM、余量 60 RPM，合计任意连续 60 秒不超过 1,200；其他 Provider/Parent 限额同样计入测试。此处是约束，不是本轮已经完成的容量验证。

工具参数只包含当前动作必要的输入与稳定引用，不重复嵌套整份状态。现有工具 schema 体积已超测试门槛，增加交通合同必须同时审查上下文开销，不能靠扩大窗口或提高门槛解决。

## 6. 验收用例：从真实旅行者出发

以下测试输入是场景，不是对真实班次、价格或设施的事实声明。先准备同一组可独立核对的测试资料；第三方不可用时允许显式模拟数据，产品业务、真实模型/工具、HTTP 与 PostgreSQL 仍贯通。

| 用例 | 用户表达 / 变化 | 用户可见与持久化断言 |
| --- | --- | --- |
| T01 高铁往返 | 两位成人去上海两天一晚，想少赶路，最后一天必须按时回杭州 | 去返程及两端接驳连续；不凭记忆写车次；到站/办理余量与当天活动不冲突；两天和餐次完整 |
| T02 晚班飞机 | 落地较晚、有托运行李，希望公共交通到酒店 | 区分落地与能离开机场时间；核查末班/运营日期；赶不上时给可行替代及费用影响，而非默认地铁或全局失败 |
| T03 长辈与行李 | 三位同行人、一人连续步行最多 500 米、两个大箱子 | 逐人要求参与方式比较；车辆容量/行李和接驳步行不被忽略；未知设施不算满足硬要求 |
| T04 酒店局部替换 | 只换酒店，午晚餐、景点和到访时间尽量保留 | 三次酒店到访身份一致；重算相关交通和费用；固定时间不成立时解释具体冲突，不偷改其他活动 |
| T05 只改预算 | 总预算提高到 8000，不要查资料、不要重排 | 预算真实保存，站序/到访/候选保留；不因否定词误进规划专用工具集；回复与数据库一致 |
| T06 景区交通 | 不开车，下午去大景区，傍晚返回住宿 | 到入口和进入核心游览点分开；景交、末班和返回链有依据；票价包含项不重复计费 |
| T07 自驾/租车 | 带行李自驾多点游，最后在指定地点还车 | 驾车不显示为打车；车辆、停车、步行和取还车连续；费用缺口明确；新方案满足还车期限 |
| T08 行中变化 | 出发晚了、当前活动排队太久，或天气使户外项目不可行 | 保留已完成/已订/锁定安排，更新剩余部分；给出受影响段与可执行替代；不重做整个旅行 |
| T09 不完整来源 | 餐饮或某段路线暂时无数据，之后来源恢复 | 部分草案和其他候选可见；补查仅填相应缺口；缺数据时不伪造地理折线、价格或成功状态 |
| T10 必要问题与跨端 | 尚缺日期或返程最晚时间；两端同时回答 | 一次一个关键问题，回答自动接续；旧答案/重复点击幂等处理，不覆盖新决定；刷新保留结果 |
| T11 长行程与恢复 | 两日 13 次以上到访，采用后改预算，再重启 Worker | JSONB 回读无损；计划身份/到访/证明状态一致；仅恢复未完成步骤，不能重复业务写入 |
| T12 取消与配额等待 | 执行中取消，或账号短时额度不足 | 取消阻止迟到提交；等待保持非终态并释放 Worker；继续时原期限/预算不重置，无需手动反复继续 |

新行程采用后至少核对浏览器、公开 HTTP 结果和 PostgreSQL 三处。录入、回答、采用、刷新通过前，不能只用自动化 green 代替。既有用户/Trip 隔离、锁定/权限和业务写入保护继续作为相关回归。

共享合同/Runtime 变化按项目规则执行 `npm test`、`npm run typecheck`、`npm run check`；受影响小程序执行对应检查。数据库测试使用隔离 PostgreSQL；缺凭据/来源必须写未验证，不跳过后声称通过。当前 CI/CD 只有本地脚本证据，主线程需核查并补齐需要的 CI 检查，生产部署不由本次文档交接自动授权。

500 用户在线、500 个复杂规划持续推进仍是既有独立容量门槛；模拟来源、单用户浏览器或单次构建不能关闭它。新增查询扇出和模型调用必须计入 Provider 配额、连接池、重试与等待成本，实际测量按原容量方案进行。

## 2. 为什么必须改变设计

当前已采用时间线存于 environment.mobility，可随路线证明一起清除；工作草案依附 pending proposal 与短期预览；计划身份、来源更新、模型快照和运行身份也没有统一交接。增加上下文窗口不能恢复已被覆盖的业务成果。

现有原生 Pi 每次调用刷新事实、独立 Child 快照、Jev 判断和 execution continuation 有价值，但模型所需的原目标、决定依据、活动草案、问题与完成回执仍分散。新设计把这些接为持续业务过程，保留原有唯一 Trip Runtime 提交权及 PostgreSQL 保护。

## 3. 证据及结论边界

### 3.1 已有真实用户路径证据

[电脑操作 QA](./2026-09-22-computer-user-qa.md)含真实 Parent/Jev、HTTP、隔离 PostgreSQL、浏览器及原始记录；C01–C07 旅行来源受控，C08 使用配置的真实来源。手机视口不是手机真机。

- C05：6 个地点仍在，7 次到访时间线丢失；补无障碍要求同时补充抵达方式，绕过狭窄保留分支。失败和继续失败出现旧候选引用、analysis_run_identity_conflict。
- C07：预算回答保存后，后续失败，草案不再可见。
- C08：只补查 food、返回 empty_verified 后其他候选也丢失；工具 input_rejected，页面却显示路线已核验。
- 末段模型账户出现余额不足；不能把所有早期失败归因于余额，也不能把无法执行的取消场景算通过。

### 3.2 侧线程补充复现

以下于本侧线程用现有真实业务方法、仅内存 repository、既有受控路线 fixture 执行，无外部 API/数据库写入。结果属于确定性代码复现，不是新一轮真实用户验收；终端输出保留于本次侧线程。

| 操作 | 观察结果 | 重建回归时的业务断言 |
| --- | --- | --- |
| 对已采用单日 5 站调用 refreshTripMobility | 10:00 寄存、16:00 入住变成 09:30 入住等新时段 | 刷新只改变报告，原计划到访/用途/时间不变 |
| 同样刷新但 route Provider 不可用 | 多站时间变成 null，角色也改变 | 失败不覆盖原计划 |
| 形成 5 站 trial 后模拟时钟前进 16 分钟 | 接口 needs_recheck、无时间线；proposal.itineraryPlan 仍在 | 证明过期后完整草案仍可查看，采用资格失效 |
| 草案预算从 8,000 提高到 9,000 | 带 itinerary 的 pending proposal 消失 | 草案保留，仅预算报告更新 |
| 草案首次取得无风险天气 | pending proposals 从 2 变 0 | 天气更新只使相关报告/问题变化 |
| 重建 planning Coordinator 后直接重放同一业务 attempt | 路线调用从 1 次增至 2 次 | 语义操作回执跨进程可复用 |
| 新鲜受控候选中只补查素食，返回 empty_verified | 住宿、游玩、交通各 3 个均保留 | 反例：局部补查不总会删除；需定位真实 C08 特定拒绝原因 |

重建方式：复用 tests/itinerary-planning-harness.test.mjs 中的候选、计划和路线资料定义，调用 createTrip → proposeTripChange → planItineraryTrial → acceptTripChange → refreshTripMobility / getTripPlanView；时间过期用服务 clock。无需运行模型即可先建立上述行为红测。不要动态执行整个测试文件或把受控数据称为真实来源。

Coordinator 复现仅证明内层业务入口依赖内存去重，尚未证明每种完整 Worker 恢复路径都重复调用。C08 具体暂存拒绝原因仍未完整重放；研究入口存在保留失败后保存废弃状态的风险分支，不能把疑点写成完整根因证据。

## 5. 迭代顺序

### 第一步：先证明失败与定义合同

复查 dirty 工作区与现有改动，保留所有他人/前序工作。从上述路径建立当前失败的行为回归；冻结计划到访、用户要求、证据和预期差异。明确 TripState、Context Pack、工具回执、客户端 projection 的同一合同。

### 第二步：完整打通一条调整路径

实现持久计划和稳定到访；保存新要求只标记相关问题。同步完成 Parent 当前上下文、局部变更、路线只读核验、草案保存与视图。用“采用 → 新无障碍要求 → 自动补查 → 可解释草案/缺口 → 刷新”贯通，不在只完成存储字段后宣布阶段可用。

### 第三步：接通判断、等待与跨端恢复

将 Jev 从候选打分消费扩展到已验证的问题合同，保留未校准分支的 Parent 处理。持久步骤/回执与原生 checkpoint 接续；加入用户回答、候选更新、部分失败、模型切换、摘要、取消和另一端改条件。

### 第四步：迁移、真实 QA 与容量

幂等迁移可核对的旧 itinerary/草案；切换后只保留一个写入来源。旧客户端和旧 Worker 兼容需明确：不认识新合同的写入不得覆盖新计划；兼容字段只作投影。回滚也必须保留新数据，不退回会覆盖计划的旧写入语义。

新路径经隔离 PostgreSQL 和真实模型/Provider 验证后再扩大容量检查。逐阶段把“设计/实现/受控验证/真实验收/未通过项”写回文档；用户已授权交接开发，无需逐章重新询问。

## 6. 业务与上下文共用验收矩阵

| ID | 用户行为/扰动 | 必须同时观察到的业务和模型结果 |
| --- | --- | --- |
| CP01 | 已采用后刷新路线/路线失败 | 到访、时间、用途不变；模型仅解释报告变化 |
| CP02 | 草案超时、服务重启、重新进入 | 草案完整可见；核验过期；上下文可从保存状态重建 |
| CP03 | 只提高预算/只有新天气 | 原计划保留；只处理受影响判断 |
| CP04 | 无障碍要求与抵达信息同时更新 | 原版可比较；明确影响及补查；无默认时间替换 |
| CP05 | 换酒店和晚餐 | 午餐及其他安排保留；同酒店重复到访不丢；费用按实际用途 |
| CP06 | 必要问题回答后模型失败 | 回答幂等已保存、草案仍在；再次接续不重问或从头研究 |
| CP07 | food 无结果/局部保存失败 | 无关候选原样保留；陈旧候选标记；下一步有明确资料缺口 |
| CP08 | 另一端增人数/改日期，旧判断迟到 | 旧结果不覆盖新事实；相关重算、无关复用 |
| CP09 | 新旧候选版本与恢复 attempt | 引用交接清楚；无 ID 猜测、无身份冲突循环 |
| CP10 | Worker 在查询/提交/回执边界退出 | 有效结果复用；写入回执去重；结果不明继续保护 |
| CP11 | 排队限流、取消、达到总期限 | 释放 Worker；期限不重置；迟到结果不能提交 |
| CP12 | 中文否定/纠正/只查酒店 | 原话顺序、目标和领域一致；不暗改硬要求 |
| CP13 | 历史摘要、切换模型、长计划分阶段 | 目标/授权/所有必要到访持续；假设不升级为事实 |
| CP14 | Jev 高置信错误、分歧、失效或未校准 | 代码硬约束仍生效；Parent 有可消费的问题与材料 |
| CP15 | input_rejected、partial、真实价格单位 | 页面与回复准确反映业务结果；关键变化不被折叠隐藏 |

首次完整规划与局部调整都要覆盖。验收对照整份到访清单、时间与角色、费用单位、授权/锁定、依赖版本、实际写入和用户可见内容，不能仅检查 selectedNodeIds 或 completed。

## 7. 验证层级与交付

- 开发时运行相应聚焦行为测试；影响共享合同/Runtime/持久化后执行 npm test、npm run typecheck、npm run check。修改小程序/共享客户端合同时再运行对应端检查。
- 真实 QA 用独立 PostgreSQL、真实 Parent/Jev、HTTP 和浏览器，明确标记每个旅行来源为受控或真实。补查路线/设施的真实来源缺失时保留未验收状态。
- 在固定相同场景对比基线与新方案：首个有用结果、完整草案时间、必要提问次数、重复/无进展调用、错误、成本及上下文大小；不要用提高预算获得表面完成。
- 500 在线与跨端订阅/重连，以及 500 复杂规划持续推进两类分别验收；后者包含冷缓存、条件更新、取消和至少 30 分钟负载。实际 Parent/Jev/Provider/数据库限制计入，受控结果不得冒充真实容量。
- 保留 Jev 1,200 RPM 总约束及现有公平调度；新增模板使用 off/shadow/auto 与独立中文校准。最新凭据、模型余额及真实路线配置应重新核对，旧 QA 状态不代表当前已恢复或仍阻塞。
- 交付代码、迁移与兼容说明、文档、可复现证据和未通过项。不能仅交设计、契约测试或防误采用拦截。

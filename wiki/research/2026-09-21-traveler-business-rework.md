2026-09-21 · 依据用户对上一轮“强行截断、自我验证式修复”的纠正

## 结论与纠正

上一轮确实修复了一部分错误写入，但没有完整修复规划业务。特别是把成功试排当作终点、强制结束 Parent，再用固定文字覆盖回复，会掩盖仍未完成的比较、补查和交付。本轮撤掉这些早停路径，修复真实控制链和持久状态后重新 QA。

**本轮代码和针对性业务路径已改善，仍不能据此宣布完整生产或 500 并发商用验收通过。** 模型、HTTP、PostgreSQL 与浏览器使用真实执行；除 T08 外，旅行候选和路线是明确标记的隔离测试资料。真实高德路线、无障碍通路、库存时效与容量仍需分别验收。

本报告接替[上一轮修复报告](./2026-09-21-traveler-acceptance-fixes.md)作为当前返工依据。历史失败、冻结用户输入和中间失败轮次全部保留。

2026-09-22：[受控资料与表达问题后续核查](./2026-09-22-traveler-delivery-followup.md)列明具体虚构数据、旧回复问题与交接修复。本地回归已通过，新的真实模型复验因本次会话网络限制未完成；不将表达规则更新记为语言质量验收通过。

## 查实的核心原因与处理

| 根因 | 用户会遇到什么 | 本轮处理 |
| --- | --- | --- |
| `trial_ready`、部分研究和来源不可用直接终止 Pi；试排／预算回复被模板覆盖 | 表面很快结束，实际没人审阅工具结果、说明取舍或继续处理 | 核验结果返回 Parent；只有真实等待、取消及执行预算边界可暂停；试排与预算模板仅用于模型没有输出时的事实回执 |
| 超预算或无障碍未知只返回“不能采用” | 用户被迫自己找替代项，或者被问无法回答的外部事实 | 返回具体问题和修复方向；Parent 在同一要求内比较更便宜候选、定向补查，再核验。对未知无台阶通路，换打车或删活动仍不能变成“已核验” |
| 只暂存成功试排，失败结果只在聊天里 | 助手说草案还在，工作台却没有东西可看 | 成功／失败草案使用同一提案和持久预览仓库；Web 可查看最新未通过草案，按钮不可采用；刷新可恢复 |
| 将“你比较并选择合适的酒店”按关键词视作用户确认 | 屏蔽建 Trip／研究工具，直接要求用户先选一个候选 | 恢复 Parent 的比较和规划工具；真实提交仍要求用户点名现有候选及明确授权，选择可撤销草案不等于采用 |
| 完整性只看有路线、状态成功；天数、晚数、用户不要的领域未清楚表达 | 一天冒充两天、酒店提前入住后漏晚餐、出差被强塞景点 | 保存 `requestedWork`、`planningDomains`、`lodgingNights`；按受托日期和领域核验，保留用户自理／休息原话；紧凑 `startAt + durationMinutes` 同样核验餐次 |
| Mobility 两层归一化都截到前 8 段；AMap 只处理前 8 地点、16 到访、8 段路线 | 第二天已有来源的路线被丢弃，Checker 误判缺资料，Parent 要用户换活动 | 删除业务证据的静默截断；保留全部已返回路线与覆盖信息；展示合同可容纳规划合同允许的所有站点，不再在 32 点处突然拒绝 |
| 用地点 ID 为多次到访复用路线 | 昨天的路线掩盖今天的证据缺失 | 按具体 `stopId` 对齐；只有旧式未排程观测保留节点匹配；缺失后续路线必须真实报缺口 |
| 同行人要求变化时把包含原站序的 Mobility 整体清空 | 已采用地点仍在，按天时间线却消失；模型误称原行程仍可执行 | 地点／日期／到达事实不变时保留原站序供对照，清除旧路线证明，标为 `needs_context`、不可采用；市内交通费用重新标为未知 |
| 工具未明确告诉 Parent 实际保存了哪些版本 | 模型把两次试排说成两份可见方案 | `savedState` 交接当前活动草案数量、替代关系、已采用项目数量、原站序是否存在及原路线状态；只有最新待采用草案，不能声称多版并存 |
| 完整行程仍复用“每个领域只选一个”的部分采用逻辑；完整调整范围又依赖关键词或保存需求工具 | 换晚餐把午餐取消，或换酒店后新旧酒店一起计费 | Parent 必填 `scope=complete_trip/selected_visits`；完整草案按全部站点提交，明确退出旧选中项，保留不受影响项目。试排前后、采用后、预算和 PostgreSQL 站序分别核对 |
| 原生工具历史在每轮重复发送，仅跨请求摘要不足以完成长修复 | 数据已经保存，模型却在最后解释时耗尽预算 | 重复状态快照以版本化回执指向最新完整快照；原生 Pi 同请求工具轮间摘要预留后续执行空间。当前事实逐次刷新，原用户输入不合并，运行预算和截止时间不提高 |
| `needs_context` 没有说明缺口由谁处理 | 缺设施资料却让游客选择“谁去核实” | 严格类型的 `resolution` 区分外部证据、方案修复与用户事实；外部证据缺口拒绝转成阻塞用户问题，继续补查或交付保留的待核验草案 |
| 补查后再次读取方案被“同参数两次”截停；参数错误消耗有效修复次数 | 还没交付就结束，错误来源引用不能纠正，最后退回泛泛的研究完成 | 只读状态读取允许继续；参数引用错误由严格校验退回、同 attempt 纠正后再执行，真实业务仍最多一次修复。总工具预算耗尽明确未完成，不能伪报成功 |
| 模型用规划偏好猜交通方式，用候选小计编预算选项 | 原来打车被说成公交；建议的预算漏算市内交通 | 提供实际 `route.modes` 和当前人数；预算取舍卡直接使用完整账本的金额和影响，用户答复前不改原预算 |

保留一个 Parent、一个 TripState、原来的业务提交入口和 PostgreSQL。没有新建编排服务、队列或额外 Agent。补查导致候选更新时，只允许在原运行、原截止时间、原修复次数内继续；用户要求、revision 或锁定发生变化时旧结果仍须作废。
